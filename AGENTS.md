# AGENTS.md

## Cursor Cloud specific instructions

DataFoundry is an npm-workspaces monorepo (Node ESM). Standard commands live in the root
`package.json` scripts, `README.md`, and `CONTRIBUTING.md` — refer to those first. Notes below
are only the non-obvious, durable caveats for this cloud environment.

### Node version (important)
- A transitive dep (`posthog-node`) plus `.npmrc` `engine-strict=true` require Node **>= 22.22.0**.
  The VM's default `node` (`/exec-daemon/node`) is `v22.14.0`, which makes `npm install` fail with
  `EBADENGINE`. Use the nvm-managed Node instead:
  ```bash
  export NVM_DIR="${NVM_DIR:-$HOME/.nvm}"; . "$NVM_DIR/nvm.sh"; nvm use 22.22.2
  ```
  The update script already runs `npm install` under this Node; run the two lines above in any new
  shell before invoking `npm`/`node` commands manually. In a login shell nvm's default alias
  (`22.22.2`) takes precedence over `/exec-daemon`, but non-login shells may not, so set it explicitly.

### Services and how to run them
- `npm run dev` starts **both** the API (`tsx watch`, http://127.0.0.1:8787) and the Web workbench
  (Next.js turbopack, http://localhost:3000/data-tasks) with hot reload. Use `-- --api` / `-- --web`
  to run just one. `scripts/dev.mjs` frees ports 8787/3000 first and rebuilds packages via `tsc -b`.
- The API serves REST at `/api/v1/*` and the CopilotKit/AG-UI stream at `/api/copilotkit`. Health:
  `GET /healthz` and `GET /ready`.
- Do **not** use `npm run start` / `deploy.sh` for development — those are the formal/production
  build+start path. For a dev environment always use `npm run dev`.

### Auth modes
- This environment is configured for **`dev` auth mode** (`DATAFOUNDRY_AUTH_MODE=dev` in root `.env`,
  `NEXT_PUBLIC_DATAFOUNDRY_AUTH_MODE=dev` in `apps/web/.env.local`). The Web UI auto-logs in as
  `dev-user` with no register/login screen; API calls use `Authorization: Bearer dev-token` and
  `X-Workspace-Id: default`.
- The alternative `password` mode (register + email verification) is documented in `README.md`; in
  test email delivery the verification token is returned in the register API response / shown in the UI.

### LLM / embedding keys
- **No LLM key is needed to start the services or load the UI.** A key (`LLM_API_KEY`, and
  `EMBEDDING_API_KEY` for knowledge features) is only required to actually run an agent data-task
  query; without it the chat send is blocked but everything else (datasource browsing, schema
  introspection, read-only SQL via Data Gateway, config API) works. Create/enable a model profile in
  the Web UI or set `LLM_*` in root `.env` to run queries.

### Local data / built-in demo
- Storage is local SQLite under `storage/` (auto-created, auto-migrated on startup). The built-in
  **"DTC Growth Review"** SQLite datasource (`dtc-growth-demo`, 5 tables) is generated by `postinstall`
  (`scripts/seed-dtc-growth-demo.mjs`) and auto-provisioned per user at API startup — good for a
  no-key smoke of schema introspection and read-only queries.

### Python sandbox (optional)
- The agent's `execute_command` tool runs Python from a repo `.venv` (numpy/pandas/matplotlib/sklearn
  from `requirements.txt`). It is only reachable when running agent queries (needs an LLM key), so it
  is **not** part of the automatic update script. To create it manually you first need the system
  package `python3.12-venv` (`sudo apt-get install -y python3.12-venv`), then
  `python3 -m venv .venv && ./.venv/bin/pip install -r requirements.txt`.
